# First principle

**Show the thing or mechanism before abstracting it.**

A generic node/box/arrow diagram is not an acceptable fallback for a concrete, scientific, spatial, or quantitative claim. If the current renderer families cannot depict the idea honestly, choose `representation_mode: "kinetic-text"` and `scene_blueprint: "animated-statement"` rather than inventing decorative geometry.

A viewer should not need to decode arbitrary shapes to understand a phenomenon that could be drawn directly.
Animate the mechanism itself: each action should visibly change the explanatory state.

# Representation decision order

For every scene choose the first representation below that can truthfully depict the spoken claim:

1. `concrete-scene`: visible physical object/state change.
2. `domain-model`: scientific or mechanistic model whose structure is part of the explanation.
3. `quantitative`: same-item/count/size/volume comparison where magnitude is the claim.
4. `spatial`: a cross-section or layered physical space.
5. `kinetic-text`: the concept cannot be pictured faithfully with a supported semantic renderer.

Do not choose a lower item merely for visual variety.

# Supported semantic blueprints

## concrete-scene

### `container-object`
Use when an object interacts with a container/fluid/region: floats, sinks, drops, rises, settles, dissolves, fills, drains.

Examples:
- ice cube in water;
- oil layer in water;
- stone sinking;
- balloon rising in air.

### `before-after-object`
Use when one concrete object visibly changes state and the before/after identity matters.

Examples:
- intact onion cell -> ruptured cell;
- sealed valve -> open valve;
- solid -> melted state when a molecular renderer is unnecessary.

## domain-model

### `molecular-system`
Use when molecules/atoms/bonds/orientation/motion are the explanation.

Examples:
- bent H2O geometry;
- hydrogen bonds forming/breaking;
- molecules moving faster/slower;
- molecules rearranging during a phase change.

### `lattice`
Use when an ordered repeated structure, spacing, or open crystal geometry is the claim.

Examples:
- ice's open lattice;
- repeated crystal structure;
- same particles occupying more space after ordering.

## quantitative

### `mass-volume-comparison`
Use when the viewer must see the same amount/count occupy different volume/size or compare two magnitudes while preserving identity.

Examples:
- same water molecules -> larger ice volume -> lower density;
- same population distributed across different area.

## spatial

### `cross-section`
Use when vertical/layered spatial arrangement is the explanation.

Examples:
- lake freezes at the surface;
- insulation layers;
- atmosphere/ocean/soil layers;
- heat or fluid moving through a section.

## kinetic-text

### `animated-statement`
Use only when none of the supported semantic renderers can depict the claim without lying or becoming a diagram of the sentence.

Animated text is an intentional fallback. It is preferable to meaningless nodes and arrows.

# Mandatory semantic fields

Every scene must provide:

- `representation_mode`
- `scene_blueprint`
- `visual_claim`
- `visual_actions`

Use `entity_refs` to name stable `entity_id` values from the episode visual ontology in the same order as `model_elements`. Never invent a scene-local id when the ontology already contains the subject.

`visual_claim` is ONE proposition the visual must make true, not a narration summary. Keep it under 180 characters.

Examples:
- `the ice cube rises until part of it sits above the water surface`
- `the same water molecules rearrange into a more open lattice`
- `surface water below four degrees remains above denser four-degree water`

# Visual actions

For every non-text semantic scene author 1-6 actions.

Each action contains:
- `actor`: canonical entity/object being changed;
- `action`: one supported action verb;
- `target`: target/location/entity, or empty string if none;
- `anchor_phrase`: a literal short phrase copied from that scene's narration.

Supported actions:
`enter`, `exit`, `move`, `rise`, `sink`, `drop`, `rotate`, `expand`, `contract`, `fill`, `drain`, `freeze`, `melt`, `assemble`, `disassemble`, `connect`, `disconnect`, `bond`, `break-bond`, `rearrange`, `flow`, `scatter`, `cluster`, `highlight`, `compare`, `reveal`, `transform`, `settle`, `cool`, `warm`, `slow`.

The `anchor_phrase` must be present in the narration closely enough for timing alignment. Use the smallest phrase that uniquely anchors the action.

Good sequence:
- narration: `As water freezes, hydrogen bonds lock the molecules into a more open structure.`
- actions:
  1. actor `water molecules`, action `slow`, anchor `As water freezes`
  2. actor `water molecules`, action `bond`, target `neighboring molecules`, anchor `hydrogen bonds lock`
  3. actor `water molecules`, action `rearrange`, target `open lattice`, anchor `more open structure`

Do NOT encode decorative animation such as `pulse`, `wiggle`, or `glow` as semantic actions.

For `kinetic-text`, return `visual_actions: []`.

# Persistent entities

Use `model_elements` as 0-4 canonical entity names and keep exact spelling stable across scenes. Prefer concrete names: `ice cube`, `water`, `water molecule`, `hydrogen bond`, `ice lattice`, `lake surface`.

Do not invent labels such as `node`, `card`, `marker`, `arrow`, `circle`, or `icon`.

At least half of explanatory scenes should reuse one or more earlier canonical entities when the script permits it. The same thing should visually remain the same thing across the episode.

# Legacy/compatibility fields

The renderer no longer uses the generic primitive as the primary production representation for new plans, but the following fields remain required for compatibility, AI-scene scoring, older tooling, and artifact continuity:

- `scene_role`
- `visual_operation`
- `visual_primitive`
- `visual_state`
- `composition_mode`
- `model_relations`
- `numeric_value` when required
- `state_before`
- `state_after`
- `key_text`
- `character_cut_in`
- `sound_cue`

Choose them honestly, but NEVER distort `representation_mode` or `scene_blueprint` to fit a primitive.

`model_relations` still describes real relations between `model_elements` with `causes`, `blocks`, `becomes`, `feeds`, or `contains`. Use `[]` when not applicable. Indices are zero-based into this scene's `model_elements`.

`numeric_value` is mandatory as a bare number whenever `visual_operation` is `counter` or `visual_primitive` is `quantity`; omit it otherwise.

Use only these compatibility pairs:
- `stack`: `particles`, `objects`, `hierarchy`, `nested-context`, `quantity`, `shells`
- `timeline`: `timeline`, `cause-chain`, `path`, `map`, `rays`, `wave`, `spectrum`, `cycle`, `particles`
- `counter`: `quantity`, `particles`, `objects`
- `compress`: `particles`, `objects`, `many-to-one`, `physical-transformation`, `before-after`, `shells`
- `group`: `network`, `one-to-many`, `many-to-one`, `facets-around-center`, `overlapping-sets`, `nested-context`, `particles`, `objects`
- `sort`: `objects`, `hierarchy`, `quantity`, `timeline`
- `scale-compare`: `before-after`, `physical-transformation`, `spectrum`, `quantity`, `objects`, `overlapping-sets`
- `payoff`: any declared primitive

`visual_state` is renderer state, NOT the script's beat names. Map correction, implication, and resolved objection beats to `mechanism`; use `payoff` for the recap.

# Character bookends and restraint

- Scene 0 is `character-hook`, `composition_mode: "bookend"`, `character_cut_in: "both"`.
- Final content scene is `recap`, `visual_operation: "payoff"`, `visual_state: "payoff"`, `composition_mode: "bookend"`, `character_cut_in: "both"`.
- Middle character appearances are optional and must remain <=35% of scenes.
- Mechanism scenes should normally use `character_cut_in: "none"`.

For `bookend` or `reaction`, provide the required listener/speaker emotion, gesture, and gaze fields from the schema. Omit those fields from full-model scenes.

# Text restraint

- `explanation_title`: only scene 0; empty elsewhere.
- `state_before` / `state_after`: short phrases, well under 32 characters.
- `key_text`: short phrase under 48 characters.
- never paste narration sentences into labels.

# Anti-generic self-check

Before returning each scene ask:

1. Could this same visual work for an unrelated topic if I changed only labels?
   - If yes, the representation is too generic.
2. Does the visual show something narration alone cannot?
   - physical state, mechanism, spatial arrangement, magnitude, or transformation.
3. Do the authored actions change the explanatory state rather than merely add motion?
4. If the concept is unsupported, did I choose `animated-statement` rather than fake a diagram?
5. Will the final scene reconstruct/resolve the opening visual question rather than end on a slogan?

# Episode-level rhythm

A good episode should vary semantic representations because the explanation changes, not because a quota demands novelty. Do not force a different blueprint when continuity is more useful. Conversely, do not repeat one blueprint across a long stretch when the narration has moved to a different type of claim.
