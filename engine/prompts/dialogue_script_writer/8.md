## Target

Write a short cartoon episode where the useful idea emerges because a character needs it right now. The viewer should understand the situation in the first five seconds, see a central object/problem, watch a visible attempt, learn one practical idea, and get a payoff that returns to the opening with changed behavior.

Before writing, silently choose:

- `opening_problem`: the concrete lived moment;
- `central_object`: the visible object, interface, habit, or trigger;
- `character_goal`: what one character wants right now;
- `failed_attempt`: a visible middle escalation;
- `midpoint_turn`: the moment understanding changes;
- `practical_action`: the concrete fix;
- `payoff_resolution`: the final changed-behavior beat.

## Natural dialogue hard rules

The last doorway-effect render failed because the lines sounded staged: repeated incantations, textbook terms, and unfinished filler. Do not repeat that pattern.

Required:

- At least half of all spoken lines must be 10 words or fewer.
- At least one short interruption, objection, or fragment every 5-7 lines.
- Use contractions and ordinary speech: `I'm`, `you're`, `that's`, `don't`, `can't`, `it's`.
- Use one idea per line. Let the next line respond to it.
- Keep facts conversational and motivated by what the character sees.
- Prefer physical, present-tense lines: `The charger was right here.`, `Wait. This is the kitchen.`, `Say it before you cross.`

Forbidden:

- repeating the same phrase three times in one line;
- lines ending in `...`;
- definition phrasing: `is called`, `this means`, `the reason is`, `in other words`, `research shows`, `studies show`;
- exposition handoff phrases: `By that`, `basically`, `actually tested this`, unless rewritten as a human response;
- generic reactions: `That's fascinating`, `Exactly`, `Interesting`;
- textbook nouns unless a character immediately needs them. Say `your brain refreshed the room` before any formal label.

Bad:
```txt
HOST: Phone charger. Phone charger. Phone charger.
BUDDY: By that, it's called the location updating effect.
HOST: Okay, so what do I actually do about...
```

Good:
```txt
HOST: Charger. I came in for the charger.
BUDDY: You rehearsed that like a spell.
HOST: It still vanished.
BUDDY: The room changed. Your cue didn't come with you.
HOST: So the doorway robbed me?
BUDDY: More like it refreshed the folder.
HOST: Rude folder.
BUDDY: Say the cue while you cross.
HOST: Charger. Through the door. Charger.
```

## Useful fact style

Only one line may carry a compact scientific idea, and it must sound spoken. Avoid formal labels unless the approved story requires them.

Bad:
```txt
BUDDY: This is called the location updating effect.
```

Good:
```txt
BUDDY: Your brain treats the new room like a new tab.
```

Bad:
```txt
BUDDY: Researchers tested this with people carrying objects through rooms.
```

Good:
```txt
BUDDY: Same walk, no doorway, fewer memory faceplants.
```

## Topic-specific prop contract

The `point` field has a hard semantic gate.

For lateness, planning fallacy, leaving early, morning routines, schedules, estimates, buffers, traffic, or time management, `prop=phone` is invalid unless the story is specifically about phone addiction, texting, messages, or apps. Use:

```txt
clock
keys
calendar
route-map
door
coffee

```

Canonical rewrites:

```txt
phone used for time        -> prop=clock
phone used for route/GPS   -> prop=route-map
phone used for schedule    -> prop=calendar
phone used while leaving   -> prop=door or prop=keys
phone used during routine  -> prop=coffee or prop=shoes
```

For doorway/memory topics, `door` is a scene/set element, not the central foreground object. Use `prop=door` only when the visible action is crossing, opening, or leaving through the doorway. Otherwise use the remembered object: `keys`, `charger`, `document`, `coffee`, `letter`, or the concrete object from the story.

For sleep/tiredness topics, use `alarm clock`, `bed`, `coffee`, `laptop`, `calendar`, `window`, or `phone` only when the phone is the disruptor. For phone/app/message topics, use `phone`. For airplane-window topics, use `window`. For bills, use `bill`. For letters/messages on paper, use `letter`. For food habits, use the actual food.

## Action-first metadata

Every spoken scene must describe something observable in `point`. `narration` is dialogue only; `point` tells the downstream director what to show.

Use this exact compact structure for every `point`:

```txt
action=<visible action>; prop=<central object or none>; function=<story function>; value=<viewer value>
```

Good examples:

```txt
action=Host stops in the kitchen doorway with empty hands; prop=door; function=opening_problem; value=viewer sees the memory fail happen physically
```

```txt
action=Host points back toward the desk where the charger still sits; prop=charger; function=failed_attempt engagement; value=the missing cue becomes visible
```

```txt
action=Buddy makes Host say the object while crossing the doorway; prop=door; function=practical_action viewer_value; value=carry the cue across the room change
```

```txt
action=Host crosses again while saying charger and grabs it immediately; prop=charger; function=payoff_resolution callback; value=the same problem now has a usable fix
```

Bad point values:

```txt
explain doorway effect
action=Host thinks about memory; prop=brain; function=summary; value=viewer learns the concept
action=Host checks the phone; prop=phone; function=morning routine; value=viewer sees time pressure
```

## Story shape

Use a light narrative frame:

- a character is caught doing the habit;
- one character makes a small challenge;
- an object or room change causes the failure;
- the character tries a fix and almost fails;
- the payoff repeats the opening with changed behavior.

Facts must surface because a character needs them, doubts them, uses them, or is surprised by them. If a fact could be swapped for any unrelated fact without changing the interaction, rewrite it.

## Output

Produce a flat list of spoken scenes covering every story act in order. Each scene is one spoken line.

- `scene_index`: continuous from 0.
- `act_index`: the source act.
- `speaker`: cast character id.
- `emotion`: one of `neutral`, `happy`, `angry`, `surprised`, `sad`, `scared`.
- `narration`: exactly what the character says. No stage directions.
- `point`: the compact action metadata described above.

Hit each act's `target_words` within about 10%. Do not pad. Default cartoon explainers should feel like 90-115 seconds unless the source story explicitly requires longer.

## Safety and factual discipline

Never invent statistics, diagnoses, mechanisms, events, laws, or quotes beyond the approved story. Everyday feelings and behaviors are allowed, but do not diagnose viewers or prescribe treatment.

## Final self-check before output

Before returning, count and audit:

- at least half of spoken lines are 10 words or fewer;
- at least one short interruption appears every 5-7 lines;
- at least one line is a fragment;
- contractions appear naturally;
- no repeated phrase appears three times in one line;
- no line ends with `...`;
- no line uses `is called`, `this means`, `the reason is`, `research shows`, `studies show`, or `in other words`;
- no line sounds like a polished definition;
- every `point` uses the exact `action=...; prop=...; function=...; value=...` format;
- for planning/lateness topics, zero scenes use `prop=phone`, `prop=screen`, `prop=app`, `prop=notification`, `prop=message`, or `prop=text`;
- for doorway topics, the door is used as a crossing/set beat, not as a giant foreground object;
- the final line shows changed behavior instead of summarizing the lesson.
